# Design

## Context

參見 proposal.md 的動機與範圍。現有 RequestCache 會合併請求並重播完成結果，但沒有成功時間／到期判斷。五種讀取頁透過 LocalReadCache 同時讀裝置副本與雲端，且頁面要求服務 forceRefresh；InventoryHistoryComponent 的兩個查詢入口也傳入 true。watchReadPage 對前景、連線與資料異動使用同一刷新 callback。

LocalStore 同時管理 readCopies、drafts、登入世代與跨分頁失效通知；CharacterService.notifyCharacterChanged 先失效所有相關快取再通知 HUD。這個順序是既有資料一致性的基礎。ngsw-config.json 目前只有靜態資源快取，沒有業務 API dataGroups。

既有 local-read-cache 要求弱網先顯示副本，mobile-pwa 及 inventory-history 也引用副本行為，本 change 以 delta 明確取代這些契約。過去已完成的 change 保留為歷史。既有 HTML 原型已呈現 30 秒線上流程及模擬時間／請求數；原型也提供有限副本回退與手動儲存草稿的模擬。

## Goals / Non-Goals

**Goals**
- 玩家短時間返回清單即看到內容，真正需要網路時才進入載入狀態。
- 30 秒新鮮期、異動立即失效與既有寫入衝突保護共同運作。
- 保留有限的持久化唯讀副本與獨立的草稿保護。

**Non-Goals**
- 本次不導入 TanStack 套件、不改後端 API、不新增輪詢或即時推播。
- 排序 SCSS、版本更新介紹視窗與發布另行處理。

## Decisions

### 1. 用玩家操作理解資料新鮮期

成功回應記為 t0，年齡小於 30 秒可沿用，等於 30 秒即到期。讀取快取不更新 t0。各帳號／角色／資源／篩選／游標各自有身分，成功空陣列同樣可快取，失敗不快取。

預設角色入口先讀角色摘要與冒險紀錄清單。倉庫與物品異動紀錄在首次進入各自頁面時才讀取；既有閒置預載只準備畫面程式碼。若直接開啟某個子頁網址，就讀角色摘要與該頁所需資料。兩個清單的 30 秒期限各從自己的成功回應開始，切到倉庫不會重設冒險清單的期限。

例如 12:00:00 取得倉庫，12:00:10 返回直接顯示；12:00:31 返回則先載入。若 12:00:12 消耗藥水，舊倉庫與相關資料當下失效，不等到 12:00:30。

Carbon 是 IBM 的介面設計系統，本規劃參考它的清單骨架與錯誤狀態。TanStack Query 是資料請求管理工具，本規劃參考它將新鮮期與主動失效搭配的方式，使用既有 RxJS 實作。

參考：
- https://www.carbondesignsystem.com/building-blocks/core/patterns/loading
- https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults
- https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation

### 2. 共用快取只負責資料，畫面負責呈現

在 RequestCache 加入成功時間與 30 秒生命週期，保留進行中請求合併、取消與失效後禁止回填。正常讀取依新鮮期決定；手動更新略過已完成快取，但相同世代已有請求時共用它，避免連續點擊取消重發。異動／帳號失效則必須取消舊世代。

所有呼叫端逐一分類為一般讀取、明確更新、表單初始化。每次進入編輯須略過已完成的 30 秒快取，重新取得完整雲端資料及原始寫入前置標記；可共用同世代同鍵的進行中完整讀取。完整成功前禁止提交及套用草稿。角色 HUD 的 freshCharacters 須與成功讀取／失效整合，避免記憶體命中卻永久鎖住操作。

將五種頁面接到既有服務的單一記憶體快取，LocalReadCache 只在雲端讀取成功後保存副本，或在離線／暫時失敗時讀取副本。記憶體命中不讀寫裝置副本；用來源區分成功回應與命中結果。watchReadPage 可保留共用訂閱功能，按觸發原因判斷刷新。不建立第二層有獨立計時的資料快取。成功時間用單調時間計算，避免系統時鐘調整延長期限；所有者切換透過既有登入失效清除服務快取並阻擋晚到結果。

### 3. 頁面狀態與觸發時機

| 情境 | 呈現及請求 |
| --- | --- |
| 首次、過期或失效後進入 | 立即顯示導覽與結構，清單用既有骨架；詳情／HUD 沿用適合其結構的既有載入元件。成功後一次呈現該區資料 |
| 新鮮資料命中 | 直接呈現清單，與正常成功讀取畫面一致。不顯示載入、更新提示、「最新資料」、「本機副本」等來源標籤，亦不保留提示列空間 |
| 閱讀中自然到期 | 不執行請求、不清空內容、不改操作位置 |
| 返回前景 | 新鮮則維持；過期才重新讀取，以受影響區域載入狀態呈現 |
| 已知離線 | 停用正式異動；保留同帳號、未失效的已載入內容供唯讀查看，即使裝置副本保存失敗。無已載入內容才使用有效裝置副本，兩者皆無才顯示錯誤；標明取得時間及重試 |
| 恢復連線 | 可見頁先依失效／期限判斷；已失敗或已切為離線唯讀的目標重新讀取，成功後才恢復正式操作。瀏覽器 online 僅為提示，API 結果才是成功依據 |
| 手動重試／瀏覽器重整 | 重試略過完成快取；整頁重整自然清空記憶體 |
| API 401／403／404 | 沿用登入／拒絕／不存在流程，清除對應資料，不以快取遮蔽 |
| 暫時讀取錯誤 | 只有網路、逾時或伺服器暫時錯誤允許改顯示有效唯讀副本；無可用副本則提供錯誤與重試，不能顯示假空清單 |

斷線前已開啟的表單繼續保存草稿。既有完全離線唯讀草稿入口亦保留，父層角色載入失敗不可遮住草稿入口。

手機的連線提示位於角色導覽正上方，其餘頁面放在視窗底部。各區保留取得時間。離線提示使用頁面色面，沿用已確認的離線文案。載入與重連更新只呈現骨架，不顯示可見載入文字或成功提示。讀取失敗才顯示近黑底白字的「無法更新資料，請重試。」與「重試」。狀態播報不搶焦點。

### 4. 異動、歷史分頁與查詢隔離

沿用 CharacterService.notifyCharacterChanged 作為同角色失效順序：退休相關請求／快取，再通知可見頁及 HUD。涵蓋角色列表與摘要、冒險列表／詳情／預設值、倉庫、角色歷史及按使用冒險篩選的歷史。更換使用冒險須同時失效舊、新冒險。

游標清單首批過期、失效或強制刷新時重設累積頁與游標；載入更多可保留已顯示首批，但使用同一有效世代的游標，失敗只顯示局部重試，不清除成功頁。不得把新首批和舊尾頁混合。返回清單的搜尋、分類、排序、捲動狀態沿用既有導覽契約，恢復內容前先檢查新鮮期。

跨分頁沿用 storage 事件使本機已知異動立即失效；其他裝置的變更接受延遲到下一次實際讀取才反映。伺服器 updated_at 衝突檢查仍是防止舊值覆寫的保障。

### 5. 方案取捨與可及性

曾比較 A 每次等雲端、B 永遠先顯示副本、C 副本加條件背景更新。使用者選定線上模式及 30 秒新鮮期，減少來回切頁等待，也減少舊數量被替換的視覺變化。正常導覽維持一次點擊；過期時需等待，錯誤時可重試。手機不增加常駐狀態列。

載入狀態使用既有 Material／骨架元件，保留區域尺寸、焦點與捲動恢復。以有名稱的狀態區適度播報，不對 HUD 與子頁重複播報同一事件；支援 reduced-motion，不用顏色作為唯一狀態。過期不可主動移走焦點，錯誤重試後回到合理操作位置。排序膠囊寬度／右側留白列入回歸。

## Risks / Trade-offs

- 其他裝置變更可能延後到下一次有效讀取才呈現 → 已獲使用者接受，保留衝突處理及原始微秒標記。
- 慢網路下過期切頁仍需等待 → 量測首次、30 秒內返回、過期返回三種情境的請求數與呈現時間，不承諾固定體感。
- 泛用快取改動波及編輯 → 對 RequestCache 全部呼叫端核對，表單必須以完整雲端快照開始。
- 副本淘汰誤傷草稿 → 只淘汰 readCopies 的指定項目，禁止刪整個 IndexedDB 或全部 localStorage。
- 舊版頁面不認識容量上限 → 新版首次對帳時補齊大小並淘汰過期／超額副本；副本遷移或配額不足不阻擋雲端顯示。
- 新鮮期不等於資料即時同步 → 到期本身無輪詢，持續停留的頁面可長於 30 秒才刷新。

## Migration Plan

依序實作記憶體快取、頁面狀態、離線副本上限與草稿流程，再同步文件。既有副本依新規則檢查有效期與容量。瀏覽器 IndexedDB 升到第 2 版，為離線副本建立容量與取得時間索引，保留草稿資料庫及內容。若需回退前端，回退版本須保留讀取第 2 版資料庫的能力，才能繼續存取已保留的草稿。無伺服器資料庫遷移。

## 離線副本與草稿

離線副本試行上限為每帳號 2 MB（2,000,000 位元組），以資料的 UTF-8 序列化大小計算，實際瀏覽器磁碟占用會有額外開銷。保留現有七天期限和最多 100 份的限制。先淘汰無效或到期項目，仍超過容量或份數時，依最近一次雲端成功取得時間由舊到新淘汰整份副本；超大單份略過儲存。只維護大小與取得時間等必要中繼資料，不追蹤最後查閱時間，避免每次保存都讀取整個帳號的資料內容。查看副本或命中記憶體不延長七天期限或改變淘汰順位；重新從雲端成功取得並保存才更新取得時間。草稿與站點資源各自管理。

只保存玩家已主動取得的完整角色／冒險／倉庫回應，詳情按單場保存，不為離線預抓。首版維持物品異動紀錄為線上查詢，等有足夠樣本再評估是否保存首批。以「嵐」的唯讀欄位聚合試算，兩份完整清單與三場詳情約 73 KiB。這批樣本支持先保留完整清單；較大角色、IndexedDB 磁碟占用與手機載入耗時待驗收。

記憶體是目前網頁暫存的資料，重新整理或關閉後不保留；裝置副本是存於瀏覽器、可在重開後讀取的資料，受上述 2 MB 限制。斷線時保留已載入內容不代表副本已成功保存，也不延長登入期限。30 秒到期本身不清除正在離線閱讀的內容；帳號或已知資料失效仍須停止顯示。物品異動紀錄不新增持久保存，離線只保留當下已載入的頁面，不能載入更多。

中途斷線可保存原本已完整開啟的表單，離線清單的正式紀錄禁止刪除。可依帳號與版本驗證後確認捨棄本機草稿。恢復連線後，在 A 的編輯入口提示 A 有草稿；選擇檢視且完整雲端內容核對成功才預填。A、B 各用自己的目標鍵，覆蓋衝突才需要停下核對。一般詳情頁顯示正式紀錄。只有按「儲存」才提交，成功後才清除草稿。拒絕、結果不明或衝突都保留草稿，避免自動補送。

## 參考模式與取捨

- 按需讀取與快取失效。依 [Microsoft Cache-Aside](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside) 先判斷記憶體是否可用，需要時讀雲端，寫入成功後使相關資料失效。[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults) 說明新鮮期內可沿用資料，30 秒是本服務採用的值。
- 有期限的唯讀回退。參考 [Workbox 到期與淘汰](https://developer.chrome.com/docs/workbox/modules/workbox-expiration) 的有限保存概念，沿用 IndexedDB 保存業務副本；本服務採七天、2 MB／100 份限制，並按取得時間由舊到新淘汰，不採最近使用排序。
- 本機草稿與手動送出。參考 [ArcGIS Survey123](https://doc.esri.com/en/arcgis-survey123/latest/capture/mobile/submitsurveyresults.html) 的本機暫存與重新連線後主動送出。沿用我們的表單及版本檢查，由雲端確認正式儲存。
- 局部載入。參考 [Carbon 清單載入](https://www.carbondesignsystem.com/building-blocks/core/patterns/loading)，在確實等待且尚無內容時顯示骨架。

## Open Questions

本次產品規則已確認，沒有阻擋實作的待決事項。30 秒與 2 MB 的實機效果列入驗收；背景預抓不在本次範圍。
