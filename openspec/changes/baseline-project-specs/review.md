## 待討論的業務衝突

除明確標示使用者已確認的部分外，其餘建議仍待確認。影響產品行為的項目在確認之前不寫成確定規則。

### C01 — 歷史戰利品修改與補貨（核心規則已確認，程式待修正）

- 文件：SRS §2.2.4、US-008 允許修改／刪除；SRS §9.4 卻鎖定既有快照、僅可追加。SRS §2.3.2 要求倉庫消耗／刪除不改歷史。
- 程式：`AdventureEntryService.updateGainedItem` 對消耗品同步差額；找不到倉庫項目時會補建。`syncGainedItems` 每次完整儲存都處理既有項目，故沒有修改獲得數量也可能補回已移除物品。永久物品數量更新又與消耗品不同。
- 初期回饋：使用者表示一般操作符合預期，因此以保留現有體驗為基準重新檢查完整流程。
- 重新核對：前端編輯表單允許既有戰利品增刪修，並完整提交所有戰利品；永久物品每張卡片以一件儲存，消耗品可調整數量。後端對仍存在的消耗品倉庫列，已採 `max(0, 現存數量 + 新獲得數量 - 舊獲得數量)`，歸零則移除。原先建議的正差額範例其實就是現有行為，不應描述為必須新開發的規則。
- 核對範例：歷史 3、倉庫 1，改歷史為 5 → 倉庫 3；倉庫仍存在且只改備註 → 數量不變；從冒險刪除戰利品 → 刪除快照及對應倉庫項目；只從倉庫刪除 → 歷史快照保留。
- 2026-09-18 使用者手動重現：依對話測試流程刪除倉庫藥水後，重新儲存來源冒險，回報「有補回 3 瓶」。這是使用者回報，非 Agent 自行執行的測試；其餘情境尚未因此視為已通過。
- 2026-09-18 已確認決策：保留歷史戰利品可更正；獲得數量未改變時，修改名稱、備註或重存冒險不補回已移除物品；消耗品獲得量 3→5 只增加差額 2（倉庫已移除也僅建立 2）；成功儲存後再存相同快照不重複入庫；真正新增的戰利品正常入庫。
- 舊資料漏入庫的修復另行處理，不作為一般儲存自動補貨的理由；本次不新增消耗歷程系統。
- 規格位置：`specs/inventory-provenance/spec.md` 的 `Editable historical loot`、`Loot corrections preserve inventory consumption`、`New loot enters inventory`。舊 SRS §9.4 的戰利品「只能追加」敘述不作為本次基線；待文件整體收斂時更新原文件。
- 仍待決策：負差額超過現存數量的處理。C10 歸零操作及 C15 型別變更亦不包含在本次同意範圍。

後續小範圍修正（未實作）：

- [ ] 補回歸案例：倉庫仍存在的差額同步、刪除後僅改備註／名稱、刪除後 3→5、成功後重存相同快照，以及新增戰利品。

### C02 — 魔法物品數的來源與單位

- 文件：SRS §2.2.1 定義起始魔法物品取上一筆合計；HUD／倉庫異動又要求即時更新。
- 程式：後端 `getDefaults` 取倉庫 `COUNT(*)`；但前端 `AdventureFormComponent.loadDefaults` 另讀倉庫，加總永久物品 `quantity` 並覆寫表單起始物品數，與 HUD 使用相同算法。一般倉庫讀取成功時，數量為 3 的一列在兩個畫面都顯示 3；前一輪推論兩個畫面分別顯示 1／3 不適用於目前完整前端流程，予以更正。
- 剩餘差異屬 API 契約與例外情境：後端回傳列數仍與前端算法不同；前端 `quantity || 1` 將 0 當 1；新增表單倉庫讀取失敗時以空陣列計為 0。這些不能直接當作使用者已遇到的正常流程問題。
- 建議：當前持有數及新增預填值統一按永久物品數量加總；歷史冒險結算維持當時快照。須確認歷史合計與現存數的區別，以及冒險中手填數量變化和實際戰利品是否強制一致。

### C03 — 第一筆冒險的預設值

- 文件：SRS §3.3、TC-012 要求全部 null；US-005 要求開卡資料或 0。
- 程式：`getDefaults` 使用角色職業等級、金幣 0、天數 0，魔法物品另取倉庫。
- 建議：採用開卡等級／職業、金幣 0、天數 0，物品依 C02；保留使用者修正起始資源的能力。

### C04 — 補登、修改日期、刪除舊紀錄是否重算歷史

- 文件：規定以 `play_date + created_at` 找最後一筆，卻未定義插入較早日期或更改日期後如何同步。
- 程式：新增一筆就覆寫角色職業；更新前以舊日期判斷是否最新；刪除後取最新剩餘職業。可能使角色職業和依遊玩日期讀出的等級不一致。
- 2026-09-18 使用者實測：先登錄 9/18 冒險由 1 等升至 5 等，再補登 9/1 冒險升 1 等，補登紀錄結束等級為 6，但 character-shell 當前等級仍為 5。這是使用者回報，非 Agent 自行操作的結果。
- 原因核對：新增表單初始化從 `getDefaults` 讀日期最新紀錄的結束等級 5，改遊玩日期沒有重取該日期之前的狀態，因此升 1 等後送出 6。後端 `createEntry` 依新提交職業字串覆寫角色，不判斷這筆遊玩日期是否最新；HUD 的 `parseTotalLevel` 優先讀 defaults，而其查詢仍取 `play_date DESC, created_at DESC` 的 9/18 紀錄，故顯示 5。不是單純未刷新，也不能只改 HUD 為 6 就認定修正完成。
- 額外靜態推論：角色職業文字讀 `currentClassesString`，故可能已是合計 6 等，而同頁等級仍為 5；此職業文字差異尚未由使用者實測回報。
- 2026-09-18 使用者補充：補登 9/1 時起始等級鎖為 5，無法如實填寫歷史起始狀態。
- 已確認：按遊玩日期之前最近一筆冒險預填起始等級與職業；沒有更早紀錄時使用開卡狀態；允許手動更正且驗證職業等級加總一致；改日期前保護已填資料，不直接覆蓋。補登後保留後續紀錄，若前後等級／職業不連續則提示玩家確認，不自動重算。
- 規格案例：開卡 1 等、既有 9/18 的 1→5 等，補登 9/1 升 1 等時為 1→2 等；9/18 保留 1→5 等並提示不連續。已寫入 `specs/adventure-log/spec.md`，尚未實作。
- 使用者明確提醒 character-shell 也需要調整。其當前等級、職業與資源應採何種來源及更新方式仍待討論，不能只改看板顯示為最新提交的數字。
- 其他待決策：同日排序、無日期歷史資料、開卡狀態保存方式、既有紀錄改日期、刪除最新及全部紀錄後的狀態。尚未確認金幣等其他資源的補登預填策略。

### C05 — 玩家名稱是會員暱稱還是角色欄位

- 文件：US-001／003 必填可編輯；SRS §2.1.1 與 DB Migration 13 說由會員暱稱提供。
- 程式：角色表單沒有玩家名稱，DTO／Service／Mapper 仍保留 `playerName` 欄位。
- 建議：會員顯示名稱為唯一來源，角色舊欄位僅為兼容資料；需確認 API 與舊資料如何呈現，而非只移除表單必填。

### C06 — 職業／等級的表示及驗證責任

- 文件：SRS 使用 `classLevels` 陣列、甚至要求更新已移除的 `character_class_level` 表；DB 與程式已用 `currentClassesString`。
- 文件要求至少一個職業、13 選項、職業總和等於結束等級；角色編輯只能改基本資料。
- 程式：後端角色 DTO 未強制職業必填，角色更新 API 仍可改職業字串，冒險後端未驗算職業等級總和。前端另有 1–20 範圍。
- 建議：先確認規則與兼容性，不把格式重構混入此次基線；後端亦應執行確定後的規則。需討論開卡是否僅限 1／5／11 級、重複職業、自訂職業與總等級上限。

### C07 — 遊玩日期及空白子項目

- 文件：SRS §2.2.1／US-005 日期必填；TC-003 卻要求所有欄位空白也成功。活動描述在欄位表選填，§9.4 又禁止空白卡片。
- 程式：冒險前端日期必填，後端主 DTO 的日期沒有必填註解；完整儲存子 DTO 有驗證。
- 建議：主表日期必填，其他選填；可以不新增任何活動，但新增的活動描述不可空白。補寫前後端一致的拒絕案例及舊 null 日期策略。

### C08 — 休整期活動是純文字還是計算輸入

- 文件：US-005b 要求純文字且不影響計算；README／SRS 描述較接近手動資源記錄。
- 程式：活動有金幣、天數、物品欄位，`recalculateDowntimeTotals` 會覆寫主表休整期變化，儲存後編入描述文字，再以格式解析。
- 待決策：活動數值是結算唯一來源，還是可以和手動填寫的主表差額並存。須處理刪除活動、無法解析的舊文字及雙重計算。

### C09 — 迎頭趕上升級與休整期扣款

- 文件：README／US-005 要求花費休整期換取升級，未明確標示適用 AL 規則版本及費率。
- 程式：升級開關／次數直接增加結束等級；另有「迎頭趕上」活動預設 -10 天，開關與扣款非同一計算來源。
- 待決策：手動紀錄或自動扣款、每級費用、可用級別、天數不足時的拒絕規則；不憑記憶宣稱為官方 AL 規則。確認版本後若需引用遊戲規則再核對官方文件。

### C10 — 快捷消耗及歸零行為

- 文件：SRS §2.3.2 說用盡自動移除；US-016b 說先確認是否移除。
- 程式：目前倉庫列表未找到快捷扣除方法或實際使用按鈕；可透過編輯改數量。
- 待決策：是否保留快捷消耗需求；數量 0 時自動移除或保留／詢問。不得因文件寫「已實作」就標為完成。

### C11 — OAuth 合併帳號與帳號停用

- 文件：US-AUTH-003 同 Email 自動登入既有帳號；帳號模型存在 `is_active`，未完整描述各登入途徑。
- 程式：密碼登入檢查停用，OAuth 路徑沒有同等檢查；Google 驗證欄位缺省被視為通過，Discord 路徑未見 Email 驗證狀態檢查便依 Email 綁定。
- 建議：任何登入途徑均尊重停用狀態；第三方 Email 合併需明確已驗證，或要求登入原帳號後綁定。需要使用者選擇綁定 UX；安全缺口另列實作任務，不能把現況描述成安全保證。

### C12 — 離線資料與跨帳號隔離

- 文件：SRS §6、US-018、README 承諾已載入角色／冒險可離線瀏覽。
- 設定：`frontend/ngsw-config.json` 只有靜態資產／字型快取，没有 API `dataGroups`。記憶體快取不等於離線重開仍可讀。
- 待決策：離線僅開啟 App 外殼，或保留私人角色資料供離線讀取。若保留，需定義帳號隔離、登出清除、到期、更新、離線寫入提示；不得直接快取所有認證 API。

### C13 — 部署與 migration 文件

- 文件：DB 手冊要求手動逐段 SQL；舊部署計畫和 AGENTS 要求 JPA。現況為 MyBatis、Flyway，自動 `migrate` 且 baseline 為 0。
- 發現：Flyway V3 包含清空資料與固定預設帳號；與把現有資料庫直接納入 migration 管理存在資料保留風險。本紀錄不抄錄憑證內容。
- 建議：將手工 SQL／舊 JPA 計畫標為歷史；另行制定現有資料庫接管流程、備份與 migration history 驗證。不可直接在既有正式資料庫試跑，也不可隨意修改已套用 migration 造成 checksum 分歧。

### C14 — 排序、搜尋及路由

- 文件：冒險時間軸由舊到新；早期計畫包含日期搜尋；路由 `/log`。
- 程式：列表預設由新到舊，可切換遊玩／建立時間並記憶；搜尋名稱／代碼／DM／故事獎勵；路由 `/adventures`。倉庫另有稀有度排序、搜尋及同調篩選。
- 建議：路由與支援的互動依現況記錄，預設排序及是否新增日期搜尋再確認。API 升序與 UI 可排序並非本身矛盾，勿混為同一需求。

### C15 — 稀有度、數量與同調

- 文件：US-014 僅五種稀有度，SRS 包含 ARTIFACT；SRS 物品欄位未完整列出同調，API 又限定永久物品適用。
- 現況：前端與 Flyway V17 支援 ARTIFACT；數量／型別在快照與倉庫同步時有差異（C01）。

### C16 — 法律聲明入口
