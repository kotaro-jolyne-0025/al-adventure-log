# Design

## Context

本設計承接 [proposal.md](./proposal.md) 與本 change 下的能力規格。現況為 Angular 表單同時接收部分起始值與結束值，Spring Boot 服務再將資料寫入 `adventure_entry`；角色目前職業另存於 `character.current_classes_string`，V6 migration 已建立 `current_gold`、`current_downtime`、`current_magic_items`，但目前 Java entity 尚未完整映射。

`adventure_entry` 已有等級、職業、金幣、休整期與魔法物品的起始／變化／總計欄位，因此新的紙本帳本模型不需要另建事件儲存系統。主要缺口是輸入責任混亂、角色開卡職業未獨立保存、舊資料仍採第一筆資源基準，以及物品無穩定的冒險／休整期來源類型。

## Goals / Non-Goals

**Goals:**

- 讓前端只提交本次變化，後端成為初始值與總計值的唯一計算者。
- 每筆冒險保留可直接展示的初始／變化／總計快照，同時讓 character 保存目前值。
- 補登不重算後續快照，但其變化仍計入 character。
- 修改與刪除只套用該筆貢獻差額，並與冒險、庫存異動在同一交易完成。
- 以穩定欄位標示魔法物品為冒險獲得或休整期獲得；手動建立及來源不明舊資料保持 null。
- 以附加式 migration 保留既有資料，避免一次性重寫所有歷史快照。

**Non-Goals:**

- 不導入 event sourcing、CQRS、訊息佇列或新的前端狀態管理套件。
- 不自動重算補登紀錄之後的歷史快照。
- 不在這次重新設計所有職業名稱、官方規則或休整期活動規則。
- 不把舊資料的模糊物品來源猜成冒險或休整期來源。
- 不改變已確認的登入、PWA、法律頁與一般 CRUD 架構。

## Decisions

### 1. API 只接受變化，後端產生快照

新增與編輯冒險的 request DTO 不再接受可由系統決定的起始值與總計值。前端提交遊玩日期、敘述欄位，以及本次等級／職業、金幣、休整期與魔法物品變化；後端依日期順序取得初始快照，計算總計後寫回現有 `adventure_entry` 起始與總計欄位。

資源初始值保留於資料與冒險詳情作為歷史快照，但新增／編輯表單不顯示初始值，只顯示玩家輸入的變化及即時計算的本筆結算總計。前端仍可用已載入的初始快照計算預覽與負值驗證；不將初始值提交至 API。

等級與職業的變化在 API 使用結構化陣列，例如職業名稱與增加等級；服務套用變化後，仍使用既有 `starting_classes_string`／`ending_classes_string` 保存顯示快照。更新與刪除時可由兩個快照推導原貢獻，不新增另一套職業歷程表。

選擇此方案是因為現有資料表已能保存紙本帳本需要的快照。替代方案是建立通用事件表或為每種資源新增一組欄位；兩者都會複製既有資料且增加同步風險。

### 2. character 是目前狀態的唯一讀取來源

`character.current_classes_string`、`current_gold`、`current_downtime`、`current_magic_items` 保存目前值，character-shell 只讀 character。`initial_classes_string`、`initial_gold`、`initial_downtime` 保存可修正的開卡基準；新角色建立時基準與目前值相同。開卡魔法物品以無冒險外鍵的倉庫永久物品明細保存，不新增重複數量欄位。

目前總等級由 `current_classes_string` 的各職業等級加總，不另存一個容易失去同步的 `current_level`。金幣與休整期從各自開卡基準累加變化；魔法物品目前值仍由倉庫永久物品 `quantity` 加總後同步至 character。

替代方案是 character-shell 每次重播全部冒險。這會讓每次畫面載入都承擔排序、舊資料與補登例外，並重現目前「職業文字與顯示等級來源不同」的問題，因此不採用。

### 3. 等級與職業變化採只增加模型

一般冒險只接受 0 或正整數的等級／職業變化，各職業增加量總和必須等於本次總等級變化，套用後總等級不得超過 20。更正既有紀錄時可把原正變化調低，但結果仍須符合上述條件。

這與目前升級及迎頭趕上流程一致，也使刪除只需撤回原正貢獻，不會產生負職業等級或自動重配職業。若未來要支援洗點或降級，應另立明確功能，不把它隱含在一般冒險紀錄。

### 4. 快照排序固定且不級聯重算

計算新紀錄初始值時，以 `play_date ASC, created_at ASC, id ASC` 決定穩定順序，選取該日期之前最後一筆快照；沒有更早紀錄時使用角色開卡基準，魔法物品使用未關聯冒險的倉庫永久物品數量。相同日期以建立時間及 id 破除平手。

補登成功後只建立該筆快照並把變化加到 character，不改寫後續紀錄。編輯日期時重新計算被編輯紀錄自己的初始與總計，但不級聯更新其他快照；若與相鄰快照不連續，回傳提示資訊供前端顯示。

舊資料若 `play_date` 為 null，僅按 `created_at, id` 保持可讀，不作為新紀錄的日期前置快照。新資料是否允許空日期仍由 C07 規格決策處理。

### 5. 以差額更新 character，所有寫入共用交易

新增時把新變化加入 character；編輯時套用「新變化減舊變化」；刪除時撤回最後保存的變化。冒險主表、休整期活動、戰利品快照、倉庫與 character 必須在同一 Spring transaction 完成。

計算集中在既有 `AdventureEntryService` 的單一路徑及少量純函式，不建立事件匯流排或額外同步服務。Controller 仍只接收 request DTO、回傳 response DTO，不暴露 entity。

角色編輯可修正開卡基準。已有冒險時先以唯讀預覽端點計算「新開卡基準 + 所有冒險貢獻」後的目前職業、金幣與休整期；確認後在單一交易更新基準及目前值。歷史冒險快照不變，因此基準更正後若既有冒險快照錯誤，玩家可另行編輯該紀錄；在修正之前，依日期使用前置快照的後續冒險仍可能延續舊快照值。無冒險時直接同步基準及目前值。預覽計算沿用共用的冒險貢獻解析，避免另建一套帳本算法。

### 6. 魔法物品來源使用穩定欄位

在 `adventure_gained_item` 與 `inventory_item` 增加可為 null 的 `acquisition_source`，非空值只允許 `ADVENTURE` 或 `DOWNTIME`；增加 `needs_details` boolean 標示待補物品。前端只為兩個非空值顯示「冒險獲得」或「休整期獲得」標籤。玩家直接在倉庫建立或無法可靠判斷來源的舊資料保持 null，不顯示來源標籤，也不得依物品名稱、備註或自由文字推測。

沿用 `adventure_gained_item` 作為歷史物品快照，即使來源為休整期也以 `acquisition_source` 區分，不另建幾乎相同的 downtime item 表。庫存仍可透過既有外鍵連回快照及冒險。

正數變化缺少明細時建立 `needs_details = true` 的永久物品；具名明細超過正數時先提高該來源變化再結算。負數只保存歷史變化及提示，不自動選擇或刪除倉庫物品。

### 7. 舊紀錄以模型版本相容，不破壞快照

在 `adventure_entry` 增加 `recording_model_version`，既有資料回填為 1，新建立的變化式紀錄為 2。版本 1 保留現有起始／結束快照與「最先建立紀錄提供資源基準」的相容計算；版本 2 只把使用者提交的變化視為 character 貢獻。

這個版本欄位避免為了套用新模型而改寫舊玩家看到的歷史數字。舊紀錄只改名稱、日期或備註時維持版本 1；若日後需要完整轉為版本 2，使用獨立、可預覽的資料修復流程處理，不在一般儲存中猜測轉換。

### 8. 職業識別值與顯示文字分離

資料庫與 API 一律使用標準英文職業識別值（例如 `Warlock`）；前端透過職業對照表顯示中文名稱。舊資料中的中文或中英並列職業字串由 V21 migration 正規化，API 收到舊中文別名時也會先轉為標準英文值。如此角色開卡基準、冒險快照及目前職業計算會比較同一個識別值，顯示譯名則可獨立調整。

## Risks / Trade-offs

- [版本 1 與版本 2 暫時共存，服務計算多一個分支] → 將分支限制在單一貢獻計算函式，並以 migration 後的固定版本值避免內容猜測。
- [補登後歷史快照可能不連續] → 保持快照不變並回傳提示；character 仍按所有變化累計。
- [職業仍使用字串快照，解析格式可能不一致] → API 使用受控職業選項與結構化變化，後端統一序列化；不在本次建立第二套職業表。
- [舊資料可能缺少起始職業或使用無法解析的格式] → migration 只做可確定的回填，無法解析者標記報表並保留原值，不靜默改寫。
- [倉庫數量與 character 魔法物品數可能因中途失敗分離] → 倉庫與 character 同交易更新，失敗全部回滾。
- [目前無法區分手動建立與來源不明的舊物品] → 兩者都不需要來源標籤，統一使用 null；只有出現實際產品需求時才擴充類型。

## Migration Plan

1. 備份並在測試資料庫演練 migration；不得直接以正式資料庫作第一次驗證。
2. 以附加式 Flyway migration 新增：
   - `character.initial_classes_string`
   - `adventure_entry.recording_model_version`
   - `adventure_gained_item.acquisition_source`、`needs_details`
   - `inventory_item.acquisition_source`、`needs_details`
3. 既有 adventure 回填版本 1；角色 initial classes 優先取最早可解析的冒險起始職業，沒有冒險時取目前職業。既有物品僅在來源可由外鍵確定時回填 `ADVENTURE`，其餘保持 null，不猜測來源。
4. 將 V6 已有的 current resource 欄位映射至 entity、mapper 與 DTO；部署後先維持既有數值，不以未驗證的歷史重播覆寫。
5. 部署後端變化式 API 與交易計算，再部署前端變化式表單及紙本帳本顯示，避免前端先送出後端不理解的新契約。
6. 執行資料一致性報表，比對 character 目前值、冒險貢獻與倉庫永久物品加總；人工處理無法解析的 legacy 資料。
7. 回滾時先回退應用版本；新增欄位保留，避免遺失已寫入的版本 2 與來源資料。確認無版本 2 新資料後，才考慮另行移除欄位，正常回滾不做破壞性 drop。

## Open Questions

- C07 決定新紀錄的遊玩日期是否必填後，再決定是否將資料庫欄位收緊為 `NOT NULL`；目前設計已定義 legacy null 日期的讀取方式。
- 無法解析的舊職業字串需要由資料一致性報表列出，實際數量須在測試資料庫演練後才能確定。
