# Design

## Context
參見 proposal.md。表單的 endingLevel 由 levelUp/catchup/catchupCount 推導；休整期另由活動清單加總。編輯初始化把總等級差的第一級視為普通升級。API 只接收 levelChange/classChanges 與休整期合計；資料庫既有 catchup_count 預設 0 不能代表已完成連動的新紀錄。線上既有多級紀錄可用休整期扣除量核對推定次數；只處理等級差與每級 10 天總扣除完全相符的紀錄，避免把不明支出改成升級原因。

## Goals / Non-Goals
Goals：方案 A 單一入口，前後端都防止漏扣／重扣，往返編輯及草稿可還原，精確回填能由既有等級與休整期數值確認的舊紀錄，維持交易與其他歷史快照安全。
Non-Goals：不改變任何冒險的休整期總值、不重算後續歷史、不推定數值不吻合的紀錄、不改全部活動資料模型、不自動修復其他錯帳。

## Decisions
### 1. 操作與摘要
升級區採使用者選定的方案 2。起始與結束等級並列，普通升級用核取方塊，迎頭趕上用單一數字欄，0 表示不使用。欄位下方顯示休整期花費，資源算式的休整期項目包含該花費。職業配置只在需調整時顯示不一致提示。

上方保留迎頭趕上及次數控制，普通升級獨立。下方移除迎頭趕上快捷預設，改為由次數衍生的唯讀摘要，不另儲存可刪除的自動活動列。變更次數不移動焦點；取消只移除衍生項，其他活動不變。沿用既有 Material 表單，錯誤連結至對應欄位，摘要文字可由輔助技術讀取，不只用顏色。

已比較 B（休整期為唯一入口：操作集中但手機須往下找）與 C（獨立視窗：清楚但多一步與焦點負擔）；使用者已選 A，學習與操作成本最低。方案選定不等同新提示文案已核准。

### 2. 明確次數與唯一計算
新增可為 null 的 linkedCatchupCount API／資料欄位：null 為舊模式，0 為新模式但未使用迎頭趕上，正整數為使用次數。不重解釋既有 catchup_count 的歷史值。
新模式 levelChange - linkedCatchupCount 必須為 0 或 1（普通升級）；職業變化合計仍須等於 levelChange。結束等級不得超過 20，不可用截斷方式隱藏超額次數。
新模式請求中的 downtimeDowntimeChange 定義為其他活動合計，後端統一減去 10 × linkedCatchupCount 再存入既有總休整期變化欄位。回應保留原有「含全部扣除」合計語意；新表單載入時以合計加回已知扣除還原其他活動值，不能再扣第二次。詳情顯示由次數衍生的摘要，不建立第二份金額來源。舊模式請求維持原契約。公開 DTO、完整儲存與單筆更新入口都必須經相同正規化驗證，避免某入口繞過。
AdventureContribution 仍讀已正規化的總變化，沿用舊貢獻扣除／新貢獻加入；重新儲存相同內容不改角色當前值。

### 3. 舊紀錄與舊草稿
沒有新欄位的紀錄及草稿預設保持舊模式。V32 migration 只在 `ending_level - starting_level > 1` 且 `downtime_downtime_change = -10 × (ending_level - starting_level - 1)` 時，將 `ending_level - starting_level - 1` 回填為 linkedCatchupCount。回填只寫明確原因標記，不改休整期總值、活動描述、character 貢獻或其他快照。新建表單及新建草稿使用新模式。
無法精確符合條件的紀錄留在舊模式，編輯時沿用原本算法，不新增轉換或玩家確認流程。新模式載入若保留舊迎頭趕上活動描述，描述繼續保留但不再把該文字列的舊 −10 再算入其他活動輸入，避免重複扣除。已是新模式的紀錄若收到舊用戶端缺欄位寫入，沿用現有 MutationGuard 409 衝突並拒絕修改，不能默默降回舊模式。草稿保存模式及次數，不保存另一份衍生扣除；舊草稿不能因缺新欄位被丟棄。

## Risks / Trade-offs
- 舊資料原因未知 → 只回填等級差與休整期扣除完全相符的紀錄；其餘保留舊模式且不更動資源。
- 同一天數被重扣 → 新模式請求只傳其他活動合計，服務端單次推導；對稱測試回應載入與再送出。
- 變更日期／兼職／高等級 → 沿用日期確認、職業分配與資源不足驗證，重新計算可用次數，保留輸入。
- 版本混用 → 後端先上，新前端後上；舊客戶端寫新模式紀錄須拒絕。舊版後端不可任意回退後繼續寫入新模式資料。

## Migration Plan
新增冪等 migration，增加 nullable linked_catchup_count 及範圍約束，精確回填可確認的舊列；其他舊列保持 null。只更新連動標記，不修改休整期數值、活動描述或其他歷史快照；不修改既有 migration。同步 entity/mapper/DTO 與 database-schema.md；驗證全新建庫、從最新已發布版本升級及重複執行。
發布前驗證新舊用戶端與後端順序。若需復原，優先保留相容後端並修正前端，不刪欄位或清草稿；回退舊後端前須確認新模式紀錄不會被舊寫入路徑破壞。此次不部署。
